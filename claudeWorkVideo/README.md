# Video Studio — Colab + Cloudflare

Video Studio is a browser interface for the existing FastAPI job service. Colab runs
Gemma2:2b through Ollama and renders with FFmpeg. Edge TTS provides online narration.
A GPU can accelerate Ollama inference. The existing frame renderer and encoder use the CPU.

## Run in your browser

1. Open `colab_postman_video_api.ipynb` in Colab and select a T4 GPU runtime.
2. Run Cells 1–4. In Cell 3, upload the updated `video_api_source.zip` from this project.
3. Run Cell 5 to start the API and Cell 6 to start the Cloudflare tunnel.
4. Open the **Video Studio** link from Cell 6. Its Cloudflare URL is already filled in.
   Paste the printed `api_token` into **Colab API token**, then select **Connect**.
5. Enter a brief and choose your output settings. Add files from your computer for
   any shared background, logo, closing artwork, background music, or scene media.
6. Select **Generate video**. Watch the stages, inspect the log or report, and
   preview or download the finished MP4 from **Render jobs**.

The API token is held in the tab. The connection uses the generated `api_token`
from Cell 6. The optional Cloudflare connector token in Cell 2 configures the tunnel.

### Open Studio locally

From this project folder, run `python -m http.server 8765 --bind 127.0.0.1 --directory studio`.
Open `http://127.0.0.1:8765/`, paste both `base_url` and `api_token` from Cell 6,
and select **Connect**. Colab still handles uploads, inference, and rendering.

### Use a supplied storyboard

Choose **Storyboard** and paste the JSON from your writing assistant. Studio also
accepts an object wrapped in a `storyboard` key. Choose output settings and attach
media using the form. Choose **Prompt** to generate from a plain-language brief.

### Optional Postman workflow

The collection remains in the source ZIP and is available from Cell 7.
Set its `base_url` and `api_token` from Cell 6 if you use it.

## Use a storyboard from a larger LLM

Import the updated Postman collection and open **Create video — supplied storyboard**.
Its config Text field contains a complete example from `example_storyboard_config.json`.
Replace the value of `storyboard` with the JSON generated by Gemini, Claude or ChatGPT.
Keep `output`, media, voice and upload settings alongside `storyboard` inside config.
A prompt is optional for this workflow. The storyboard provides the content and total duration.

Gemma writes each slide's heading, description, supporting text, callout and top-right header
from that scene's key points and guidance. Spoken narration and scene order come from your
storyboard. Timing adjustments may shorten narration as recorded in the job report.
The storyboard workflow requires a professional tone. Omit voice.tone or use professional.

The number of scenes is the length of the supplied scenes array, from one to forty.
Scene numbers must start at 1 and follow in order. scene_count must match this array.
Scene target times must add up to main_content_seconds, which together with closing time
must add up to duration_seconds. These scene times guide initial allocation. The final scene
timings follow measured speech while the total remains within ±3 seconds.

A conflicting explicit duration or closing setting returns a field error. You may supply
closing_slide.file_field for custom artwork and keep the storyboard's closing duration and
message. A zero-duration closing with an empty message disables the ending.

The header summarizes the scene’s subject and main change or takeaway. It wraps in its own area with a gap from the logo. A wide custom logo is scaled
to fit its reserved area. Text that exceeds the readable header space is shortened on screen.
If Gemma exhausts its display-generation retries, the app can use display text taken
directly from the supplied purpose and key points. storyboard_display_log records that fallback.

Use `larger_llm_prompt.txt` as the reusable prompt to generate the storyboard JSON.
A standalone copy of that JSON belongs inside `config.storyboard` in Postman.

## Upload actual media in the same request

Open **Create video — supplied storyboard** and select **Body → form-data**.
The example has the following rows.

| Field | Postman type | What to provide |
| --- | --- | --- |
| `config` | Text | Storyboard and media mappings from `example_storyboard_config.json` |
| `company_logo` | File | Custom JPG, PNG or WebP company logo |
| `background_video` | File | Background MP4, MOV, WebM or MKV |
| `scene_2_media` | File | JPG/PNG/WebP, GIF, or another video |
| `closing_slide` | File | Static JPG/PNG/WebP QR code or brochure |

Click each File row and select its real file. Keep the `config` row as Text.
Let Postman supply the multipart Content-Type and boundary automatically.

Each `file_field` inside config names the matching File row. You may choose other
field names such as `scene_3_media`, but they must match exactly. Every uploaded
file must be referenced; every referenced file must be uploaded. Do not send asset
IDs, Colab paths, Windows paths or arbitrary URLs. Multiple references can reuse
one uploaded file. Add more File rows for additional media.

To skip any upload, uncheck its File row and remove its reference from the config.
Omit `brand.logo_file_field` and `closing_slide.file_field` to use the bundled Savvy
Asia logo and card. To omit the card entirely, set the storyboard's closing duration
to zero and use an empty closing narration. Rebalance the scene times so they add up
to the video's total duration. Remove the closing File row and its config reference.
Custom uploaded closing artwork uses the timing and message in `storyboard.closing`.

The supplied storyboard example uses four main scenes. Scene numbers are one-based.
Set `scene_media[].scene` to an existing scene in your storyboard. Each scene can
have up to four sequential media assets. Shared backgrounds advance with the final
timeline, and a scene override takes priority.

## Defaults and behaviour

GET `/options` returns defaults, descriptions, fit/motion meanings and a complete
example. GET `/schema` returns nested types, bounds and enum values. GET `/voices`
returns the current Edge voice catalog; `/voices?locale=en-US` filters it.

| Setting | Default | Meaning |
| --- | --- | --- |
| duration_seconds | parse prompt, then 60 | Explicit field overrides prompt duration |
| output | 1920x1080, 30 FPS | Even 16:9 dimensions; up to 1080p and 60 FPS |
| voice.name | en-US-BrianNeural | English narration; use an available Edge ShortName |
| voice.tone | auto | auto/professional/calm/enthusiastic/urgent |
| rate/pitch/volume | 0 | Numeric base offsets; tone presets also contribute |
| narration_gap_seconds | 0.18 | Short inter-scene voice gap plus frame rounding |
| transition_seconds | 0.20 | Included visual crossfade |
| fit | cover | Fill, possibly cropping. Contain preserves the whole asset |
| motion | none | Still images: none/zoom_in/zoom_out/pan_left/pan_right |
| loop | true | Repeat video/GIF; false holds its last frame |
| start_seconds | 0 | Source-video trim position, never a finished-video timestamp |
| end_seconds | end of source | Source-video trim endpoint |
| brand.logo_file_field | omitted | Use the bundled Savvy Asia logo |
| closing_slide | bundled | Three-second SavvyMan closing card |
| closing_slide.narration | default on bundled card | “Connect to Savvy Asia.” when voice is enabled. Use an empty string for silence |
| music.enabled | false | Optional generated bed or uploaded instrumental audio |

Photo motion requires a static image and `fit=cover`. Contain keeps the asset
stationary. Videos/GIFs retain their native movement. Static closing artwork is
always shown without the main template, overlays, cropping or motion. The card can
grow to fit its spoken message within the total duration window. For storyboard
jobs, the closing message comes from `storyboard.closing.narration`. For prompt
jobs, supply `closing_slide.narration` to add speech over uploaded artwork.
Background music is lowered during closing speech.

Emotion is approximated using the existing numeric rate/pitch/volume presets;
custom expressive SSML styles are not promised. Listen to the final narration.

## Duration policy

The target includes the closing slide. A 30-second request accepts 27–33 seconds.
Explicit `duration_seconds` takes priority over the duration in the prompt.
The planner measures narration at bounded speaking rates and asks Gemma to shorten
it when needed. If the normal fit is just over the limit, the app can retry the
complete narration at up to 1.12× speed inside the same duration window.
Narration plays in full, and a job fails with a timing report if
its measured audio and closing card still exceed the window. Short scripts can use
the lower end of the window to reduce silence. Reports give the signed duration
difference, and `narration_edits` records any wording changes.

## Job lifecycle and troubleshooting

`queued → running → completed` or `failed`. GET `/jobs/{job_id}` reports the stage
and completed_stages. This is a stage count, not a precise elapsed-time estimate.
GET `/jobs/{job_id}/report` returns timing, quality, cues and narration edits.
If Gemma has trouble writing a full scene, the planner retries with a smaller
narration-only request and builds the display labels from the topic and draft.
The report's `scene_repair_log` lists what was rejected and which mode recovered.
GET `/jobs/{job_id}/log` returns the last part of the job log.

- 401: set collection Bearer token to `{{api_token}}`; copy the generated token.
- 411: allow Postman to set Content-Length for the multipart request.
- 413: keep the complete request under 90 MiB and each file under 80 MiB.
- 415: use form-data; config is JSON Text, not a raw JSON request body.
- 422: read the field-level validation error; check filenames, file_field, motion and scene numbers.
- 409 on download: generation is not completed yet. Check job status.
- Failed job: read `/log`; network failures for Edge/Ollama are distinct from media or render failures.

The queue accepts ten active/queued jobs and runs one render at a time. A render
has a two-hour limit. Each job uses a separate process and folder. SQLite metadata
survives API restarts within the same runtime; interrupted running jobs are marked
failed. Queued jobs resume when the API restarts. Complete runtime deletion removes
the local jobs and token; download your results before the runtime ends.

The main log and tunnel log are under the state folder. The optional model-setup
cell must not run while a video job is using Ollama. If changing runtime settings,
stop services, make the change, then restart.

## Cloudflare and Colab limits

Quick Tunnels create a temporary public HTTPS address. They have no uptime
guarantee and the address changes when recreated. The tunnel forwards requests;
all rendering still occurs in the Colab runtime. Keep the notebook/runtime active
while testing, without attempts to bypass idle limits.

Use only where the runtime's terms permit this workflow. Managed Colab imposes
restrictions on proxy/service usage and free runtimes additionally restrict some
unattended workers and notebook-UI bypasses. A tunnel does not remove those limits.
This is a development integration, not a promise of always-on Colab hosting.

Optional named tunnel: enter a Cloudflare tunnel token and its already-configured
public URL in Cell 2. Its public application route must target the same local API
port. Browser-only email authentication on Quick Tunnels is not used, because
Postman sends the application's Bearer token instead.

- https://research.google.com/colaboratory/faq.html
- https://developers.cloudflare.com/tunnel/get-started/quick-tunnels/
- https://fastapi.tiangolo.com/tutorial/request-forms-and-files/

## Running the same code on a Linux machine you control

Install requirements.txt, FFmpeg/FFprobe and DejaVu fonts. Set VIDEO_API_ROOT and a
random VIDEO_API_TOKEN, then run:

```bash
python -m uvicorn server:app --host 127.0.0.1 --port 8000 --workers 1
```

The cloudflared connector must target that port. The same Postman collection works
after updating its base_url. The bundled pipeline stages are trusted server code,
not code submitted by API users. `runner.py --self-test` is an internal synthetic
render fixture, never a public request option and never a live-model verification.
